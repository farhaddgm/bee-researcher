# طرح فنی و برنامهٔ آزمون گفت‌وگوی خبر

تاریخ طراحی: ۲۰۲۶-۱۰-۰۸ · تأیید ۱۰ مورد نسخهٔ اول: ۲۰۲۶-۱۰-۰۹

مرجع محصول: [پیشنهاد گفت‌وگوی خبر](NEWS-CHAT-PROPOSAL-fa.md).

این سند طرح اولیه را حفظ می‌کند. نام جدول‌ها و endpointهای بخش‌های طراحی الزاماً قرارداد نهایی نیستند. قرارداد واقعی، تصمیم‌های اجرایی و شواهد آزمون در [سند پیاده‌سازی](NEWS-CHAT-IMPLEMENTATION-fa.md) آمده است. مبنای طراحی commit `7c172235be136ef31ad478a5e265318bb95f3d8f` از نسخهٔ 3.39.1 است.

## ۱. تصمیم‌های معماری و مرز تغییر

۱. گفت‌وگو یک سرویس تعاملی داخل Researcher با صف، مصرف و مجوز مستقل است؛ کار خط تولید خزش/تحلیل/انتشار را فراخوانی نمی‌کند.

۲. تاریخچهٔ اصلی در دیتابیس Researcher نگهداری می‌شود. قرارداد مشترک به یک سرویس Conversations خاص وابسته نمی‌شود تا مدل و برند قابل تعویض بمانند. OpenAI امکان نگهداری زمینه در سرویس خودش را دارد، اما انتخاب تاریخچهٔ محلی، تصمیم طراحی ماست. [مستندات زمینهٔ گفت‌وگو](https://developers.openai.com/api/docs/guides/conversation-state).

۳. اتصال هر برند adapter اختصاصی دارد؛ سازگاری همهٔ APIها با قالب OpenAI فرض نمی‌شود. کلیدهای جدید، Secret اختصاصی دارند؛ اعتبارنامه یا کد Contenter و Consultant کپی یا تغییر نمی‌کند.

۴. مدل گفت‌وگو و مدل تحلیل دو تنظیم مستقل‌اند. مدل انتخابی کاربر نباید در `analysis_model` یا تنظیمات مشترک pipeline نوشته شود.

۵. رابط در ماژول‌های محدود و قابل آزمون ساخته می‌شود، نه با چند لایهٔ الحاق کد روی DOM. migration فقط schema Researcher را گسترش می‌دهد. هیچ نیاز فعلی به بانک برداری، سرویس جست‌وجوی جدید یا تغییر دیتابیس سایر پروژه‌ها وجود ندارد.

## ۳. ساختار پیشنهادی کد

```text
app/news_chat/
  schemas.py          درخواست/پاسخ تایپ‌شده و خطاهای ماشینی
  permissions.py      مجوز کاربر، پروژه، متن و ارائه‌دهنده
  context.py          حل publication و ساخت زمینهٔ نسخه‌دار
  citations.py        نگاشت و اعتبارسنجی ارجاع‌ها
  catalog.py          فهرست مدل‌های مجاز و قابلیت‌های واقعی
  usage.py            رزرو/تسویهٔ هزینه و سهمیه
  service.py          چرخهٔ گفت‌وگو و generation
  streaming.py        رویدادهای پاسخ و قطع/بازیابی
  retention.py        حذف تاریخچه و پاک‌سازی رویدادهای موقت
  providers/
    base.py           قرارداد مشترک
    openai.py         اتصال Responses
    anthropic.py      اتصال بومی Claude
    google.py         اتصال بومی Gemini
app/static/user/news-chat.js
app/static/user/news-chat.css
```

مسیر نهایی فایل‌های static با سازوکار بسته‌بندی موجود هماهنگ می‌شود. کد و CSS فقط در صفحهٔ مرتبط فعال می‌شوند؛ listenerهای تکراری، onclickهای inline و styleهای ناسازگار با CSP اضافه نمی‌شوند. در خروج از صفحه، listener، timer و اتصال stream آزاد می‌شوند.

قرارداد adapter باید رویداد متن، ارجاع، مصرف، شناسهٔ درخواست ارائه‌دهنده و پایان/خطا را نرمال کند. توانایی stream، استناد بومی، شمارش توکن و سقف زمینه برای هر مدل capability مستقل است؛ endpoint فهرست مدل‌ها به‌تنهایی تأیید کیفیت یا قابلیت نیست.

## ۴. مدل دادهٔ پیشنهادی

| موجودیت | فیلدهای کلیدی | قید اصلی |
| --- | --- | --- |
| `news_chat_conversations` | id، user_id، assistant_id، publication_id، عنوان، زبان، وضعیت، زمان‌ها | مالکیت خصوصی؛ هر گفت‌وگو فقط یک خبر |
| `news_chat_contexts` | conversation_id، نسخه، scope، هش گزارش/منبع، بخش‌های مجاز و پوشش | snapshot تغییرناپذیر، حداقل دادهٔ لازم |
| `news_chat_messages` | conversation_id، شمارهٔ ترتیب، نقش، متن، برند/مدل، ارجاع‌ها، وضعیت | ترتیب یکتا و پیام نهایی تغییرناپذیر |
| `news_chat_generations` | message_id، idempotency_key، وضعیت، attempt، deadline، cancel_requested | یک generation برای هر ارسال؛ یک generation فعال برای هر کاربر |
| `news_chat_usage` | generation_id، کاربر/پروژه، قیمت نسخه‌دار، رزرو، مصرف، وضعیت تسویه | تلاش‌های ناموفق/مبهم هم ردیابی شوند |
| سیاست چت پروژه و مجوز حساب | enabled، برند/مدل مجاز، scope، سقف‌ها، نسخهٔ سیاست | افزایش دسترسی فقط با اختیار معتبر |

ستون‌های پیشنهادی باید FK و کنترل تعلق به پروژه داشته باشند؛ کنترل صرفاً در UI کافی نیست. محدودیت تولید هم‌زمان با قید/قفل دیتابیس یا هماهنگ‌کنندهٔ مشترک اجرا شود، نه متغیر process-local که در چند worker دور زده شود.

نسخهٔ نهایی متن پاسخ و منابع پس از پایان ذخیره می‌شود. پاسخ لغوشده/ناقص با همان وضعیت نگهداری می‌شود و «پاسخ کامل» تلقی نمی‌شود. اصلاح سؤال ارسال‌شده یا «دوباره پاسخ بده» یک پیام/generation جدید می‌سازد؛ تاریخچهٔ قبلی بی‌سروصدا بازنویسی نمی‌شود.

snapshot فقط متن لازم و مجاز را نگه می‌دارد؛ از کپی کامل export کسب‌وکار و raw HTML خودداری می‌شود. دادهٔ خصوصی در حالت سکون و بکاپ باید تحت کنترل دسترسی و سیاست رمزگذاری متناسب زیرساخت قرار گیرد؛ این طرح ادعای رمزگذاری end-to-end یا بی‌دسترسی‌بودن اپراتور ندارد.

## ۵. قرارداد API پیشنهادی

| روش و مسیر | وظیفه |
| --- | --- |
| `GET /user/api/chat/models?assistant_id=…` | فقط مدل‌های مجاز و وضعیت امن دسترسی؛ بدون کلید یا خطای خام |
| `GET /user/api/publications/{id}/chat-context` | متادیتای زمینه و متن/بخش‌های مجاز برای بررسی استناد |
| `GET /user/api/publications/{id}/conversations` | تاریخچهٔ شخصی همان کاربر برای همان خبر |
| `POST /user/api/publications/{id}/conversations` | ایجاد گفت‌وگوی خالی؛ بدون فراخوانی AI |
| `GET /user/api/conversations/{id}/messages` | پیام‌ها و ارجاع‌های مجاز، با صفحه‌بندی |
| `POST /user/api/conversations/{id}/messages` | اعتبارسنجی، رزرو و پذیرش generation؛ پاسخ 202 |
| `GET /user/api/chat-generations/{id}/events` | اتصال خواندنی SSE به generation موجود |
| `POST /user/api/chat-generations/{id}/cancel` | درخواست توقف، با CSRF |
| `DELETE /user/api/conversations/{id}` | منع دسترسی فوری، توقف تولید و حذف طبق سیاست نگهداری |
| `POST /user/api/chat-messages/{id}/feedback` | بازخورد کیفیت پاسخ، جدا از بازخورد خبر |

درخواست ارسال شامل متن سؤال، مدل مجاز انتخاب‌شده، شناسهٔ idempotency، نسخهٔ زمینه و در صورت نیاز شناسهٔ بند انتخاب‌شده است. client نمی‌تواند user_id، system prompt، مدل/URL دلخواه، اصل خبر جعلی یا وضعیت پرداخت را تعیین کند. انتخاب متن باید به offset/بخش معتبر در snapshot سرور نگاشت شود.

مجوز ساخت/خواندن/حذف/بازخورد و اتصال مجدد stream در سرور جدا بررسی می‌شود. شناسهٔ متعلق به کاربر یا پروژهٔ دیگر با پاسخ بدون افشای وجود رکورد رد می‌شود. همهٔ mutationها از کنترل CSRF فعلی عبور می‌کنند. پاسخ‌های خصوصی `Cache-Control: no-store` دارند و در service worker یا cache عمومی ذخیره نمی‌شوند.

GET رویدادها تولید تازه آغاز نمی‌کند و فقط به درخواست از قبل پذیرفته‌شده متصل می‌شود. احراز هویت با کوکی User فعلی است؛ توکن نشست یا متن سؤال در URL قرار نمی‌گیرد. stream پس‌زمینه نشست را تمدید نمی‌کند. تغییر موضوع/کاربر/پروژه، دادهٔ حافظهٔ صفحه و اتصالات قبلی را پاک می‌کند.

صفحهٔ پیشنهادی: `/user/news/{publication_id}`؛ بارگذاری مستقیم، Refresh و Back باید کار کنند. لینک‌های قدیمی User با `news=…` در صورت وجود به همان خبر نگاشت می‌شوند و مسیر login/OAuth فعلی حفظ می‌شود. عنوان/متادیتای محتوای خصوصی پیش از احراز هویت رندر نمی‌شود.

## ۶. چرخهٔ درخواست و پاسخ تدریجی

چرخهٔ پیشنهادی: پذیرفته‌شده ← در صف ← تولید ← کامل/متوقف/ناموفق/وضعیت نامعلوم.

۱. پیش از رزرو: نشست، مجوز چت، عضویت دستیار، منتشرشده‌بودن خبر، سیاست متن، برند/مدل و سهمیه بررسی می‌شوند.

۲. در تراکنش: idempotency، سقف هم‌زمانی و سقف کاربر/پروژه/کل بررسی و هزینهٔ بیشینهٔ مجاز رزرو می‌شود.

۳. worker با deadline و نسخهٔ سیاست دوباره بررسی می‌کند و درخواست را به برند انتخاب‌شده می‌فرستد. صف تعاملی و اتصالات خروجی، منابع خزش زمان‌بندی‌شده را اشغال نمی‌کنند.

۴. SSE رویدادهای `queued`، `started`، `text_delta`، `citations`، `usage` و `completed/stopped/failed` می‌دهد. پاسخ تدریجی در OpenAI از SSE پشتیبانی می‌شود؛ نگاشت برندهای دیگر اختصاصی است. [Streaming رسمی OpenAI](https://developers.openai.com/api/docs/guides/streaming-responses).

۵. ارجاع‌ها پیش از قابل کلیک شدن اعتبارسنجی می‌شوند. متن در حال تولید «پاسخ در حال تکمیل» است؛ علامت معتبر یا تضمین صحت پیش از بررسی نهایی نمایش داده نمی‌شود.

۶. قطع اتصال مرورگر درخواست پولی تازه نمی‌سازد. اتصال مجدد با generation_id و شناسهٔ آخرین رویداد انجام می‌شود. replay محدود، خصوصی و موقت است؛ انقضای replay با دریافت snapshot پیام جبران می‌شود، نه با تولید دوباره.

۷. توقف کاربر درخواست لغو به worker می‌فرستد. وضعیت لغو قبل از آزادکردن رزرو تسویه می‌شود؛ قطع دریافت پاسخ لزوماً توقف فوری صورتحساب ارائه‌دهنده نیست.

۸. هنگام انقضای نشست، لغو مجوز یا حذف خبر، ارسال رویداد محتوا متوقف و درخواست لغو ارسال می‌شود. deadline نشست از ابتدا با generation بسته می‌شود؛ بررسی زندهٔ مجوز در stream حداکثر هر ۱۵ ثانیه و پیش از ارسال بخش بعدی طبق نسخهٔ سیاست انجام شود. هدف ابطال آنی در درخواست جدید است؛ تأخیر محدود stream باید اندازه‌گیری و اعلام شود، نه وعدهٔ توقف صفرمیلی‌ثانیه‌ای.

۹. shutdown/deploy با drain و مهلت محدود، generation فعال را کامل یا متوقف می‌کند. job بدون نتیجه پس از restart به وضعیت نامعلوم می‌رود؛ دوباره به‌صورت خودکار خریداری نمی‌شود.

### تکرار و قطع شبکه

دو کلیک یا retry همان idempotency_key باید همان generation را برگرداند. این ضمانت محلی به معنی exactly-once قطعی در سامانهٔ بیرونی نیست: اگر ارائه‌دهنده درخواست را پذیرفته باشد اما پاسخ شبکه گم شود، وضعیت پرداخت ممکن است مبهم باشد.

پس از شروع پاسخ، timeout مبهم یا قطع شبکه، retry خودکار و تعویض برند ممنوع است. اگر API راه امن بازیابی همان درخواست داشته باشد از آن استفاده می‌شود؛ در غیر این صورت کاربر وضعیت را می‌بیند و برای تلاش تازه، اقدام جدید با هشدار احتمال هزینه انجام می‌دهد. retry فقط برای خطای صریحاً ردشده و قابل تکرار طبق قرارداد همان ارائه‌دهنده، در سقف محدود مجاز است.

## ۷. زمینه، استناد و کیفیت

resolver از publication_id معتبر آغاز می‌کند؛ متن خبر را از browser نمی‌پذیرد. گزارش منتشرشده همیشه با برچسب `published_report` و اصل مقالهٔ مجاز با `source_article` تفکیک می‌شوند. متن تحلیل داخلی و brief تجاری خصوصی خارج می‌مانند.

بخش‌بندی متن با شناسهٔ پایدار، هش نسخه و offset یونیکد انجام می‌شود. قرارداد offset در سرور/JavaScript صریح است تا تفاوت code point و UTF-16، حروف فارسی، نیم‌فاصله و emoji شاهد را جابه‌جا نکند. متن پاک‌سازی‌شدهٔ دقیق مبنای offset است، نه HTML خام یا ترجمهٔ متفاوت.

برای متن کوتاه، تمام متن مجاز در سقف زمینه وارد می‌شود. برای متن بلند، بازیابی فقط در همان سند و با پوشش زبان سؤال انجام می‌شود؛ محدودیت بخش‌های دیده‌شده در پاسخ قابل مشاهده است. اگر سؤال به بخش انتخاب‌نشده وابسته باشد، مدل نباید با قطعیت پاسخ دهد. خلاصه‌سازی تاریخچه نیز نسخه‌دار و دارای هزینهٔ ثبت‌شده است و به‌عنوان شاهد خبری استفاده نمی‌شود.

استناد مشترک شامل نوع منبع، شناسهٔ snapshot، بخش، محدودهٔ متن و نقل‌قول کوتاه است. URL از دادهٔ معتبر سرور می‌آید؛ لینک ساخته‌شدهٔ مدل مستقیماً رندر نمی‌شود. ارجاع معتبر باید به نسخهٔ واقعاً ارسال‌شده اشاره کند و نقل‌قول در همان نسخه وجود داشته باشد.

در Claude، استناد بومی به محل سند قابل نگاشت است. مستندات فعلی هم‌زمانی citations با خروجی JSON schema سخت‌گیرانه را ناسازگار اعلام می‌کند؛ بنابراین adapter نباید الزام یکسان JSON را روی همهٔ برندها تحمیل کند. اعتبار محل استناد، درستی معنایی ادعا را تضمین نمی‌کند. [Citations رسمی Anthropic](https://platform.claude.com/docs/en/build-with-claude/citations).

اگر متن منبع تغییر کرده باشد، گفت‌وگوی قدیمی به snapshot قبلی ارجاع می‌دهد و هشدار نسخه دارد؛ ادامه با متن جدید یک شاخه/گفت‌وگوی تازه می‌سازد. لغو حق دسترسی به منبع با وجود snapshot دور زده نمی‌شود.

## ۸. سیاست مدل و هزینه

کاتالوگ سمت سرور برای هر مدل: provider، model_id، عنوان، enabled، نسخه/alias، سقف ورودی/خروجی، قابلیت‌ها، طبقهٔ دادهٔ مجاز، مرجع/تاریخ قیمت و وضعیت دسترسی. اضافه‌شدن یک مدل به API ارائه‌دهنده، خودکار آن را برای کاربران فعال نمی‌کند. نام نمایشی جای شناسهٔ واقعی API نیست.

در نخستین عرضه مدل‌های دقیق با دسترسی واقعی حساب، کیفیت فارسی و سایر زبان‌ها، سرعت و هزینه ارزیابی می‌شوند. امکان استفادهٔ قانونی/قراردادی در منطقهٔ استقرار نیز پیش‌نیاز است؛ محدودیت ارائه‌دهنده دور زده نمی‌شود. smoke test پولی فقط پس از تأیید توسعه، با سقف معلوم و دادهٔ غیرمحرمانه اجرا می‌شود.

قیمت و مصرف باید provider-specific باشند. محاسبهٔ کلی: هزینهٔ ورودی غیرcache + ورودی cache + خروجی قابل صورتحساب/ reasoning مطابق قرارداد + ابزارها. reasoning دوبار حساب نمی‌شود اگر در همان output usage منظور شده باشد. مصرف واقعی ملاک تسویه است و برآورد با برچسب تخمینی نشان داده می‌شود.

رزرو هم‌زمان برای کاربر، پروژه و سقف سراسری اتمیک است. قیمت نامعلوم، پاسخ بدون usage، خطای مبهم و قطع پاسخ باعث صفرشدن هزینه نمی‌شوند. رزروهای نامعلوم تا reconcile یا مهلت و سیاست صریح آزاد نمی‌شوند؛ هشدار اپراتور دارند. سقف نرم API ارائه‌دهنده جای دفتر مصرف داخلی را نمی‌گیرد و reservation نیز سقف مطلق صورتحساب بیرونی را تضمین نمی‌کند.

هنگام لغو، نتیجهٔ جزئی و مصرف قابل اتکا نگه داشته می‌شود. retry پولی به عنوان attempt جدا در دفتر مصرف ثبت می‌شود. تغییر به مدل گران‌تر یا ارائه‌دهندهٔ دیگر نیازمند انتخاب کاربر است. AI چت از سهم رزروشدهٔ تحلیل خبر مصرف نمی‌کند و مجموع هر دو تابع سقف کل است.

## ۹. حریم خصوصی و امنیت

- مجوز خواندن یک خبر، مجوز خواندن چت شخص دیگر نیست. کنترل مالکیت در تمام مسیرها از جمله بازخورد، یادداشت، حذف و replay اعمال می‌شود.
- مجوز دیدن گزارش نهایی، مجوز دیدن اصل منبع پشت ورود یا اطلاعات Contenter نیست؛ scope و سیاست ارسال به هر برند جدا بررسی می‌شود.
- کلید فقط سمت سرور و در secret مستقل است. درخواست browser به دامنهٔ ارائه‌دهنده، واردکردن کلید کاربر یا انتخاب base_url دلخواه نداریم.
- ورودی خبر و کاربر غیرقابل اعتماد است؛ نقش system با متن منبع ترکیب نمی‌شود. در نسخهٔ اول مدل هیچ ابزار نوشتن، SQL، ارسال پیام، خزش یا انتشار ندارد. محدودکردن اختیار مدل، اثر تزریق دستور را کاهش می‌دهد، نه اینکه آن را کاملاً حذف کند. [راهنمای OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).
- رندر Markdown با allowlist، حذف HTML، URL امن و بدون image خارجی خودکار انجام می‌شود؛ پاسخ مدل نباید درخواست شبکه به مقصد دلخواه یا نشت داده از تصویر ایجاد کند.
- لاگ صرفاً metadata محدود و حذف‌حساسیت‌شده دارد. خطای خام upstream، prompt، پاسخ کامل، ایمیل، کوکی و header احراز هویت وارد رخداد یا شیت نمی‌شوند.
- تاریخچهٔ کاربر خصوصی است؛ پنل Owner مصرف و وضعیت سرویس را نشان می‌دهد. اشتراک متن برای پشتیبانی نیازمند اقدام صریح و قابل ممیزی است.
- در تغییر برند، سیاست مجاز داده و رضایت همان کاربر کنترل می‌شود. پیش‌فرض گفت‌وگوی تازه، جلوی انتقال ناخواستهٔ تاریخچه به شرکت دیگر را می‌گیرد.
- پیشنهاد TTL تاریخچه ۳۰ روز است؛ حذف، رویدادهای موقت و snapshotهای بدون استفاده را هم پاک می‌کند. ledger مالی بدون متن، طبق سیاست جدا نگه داشته می‌شود. زمان نگهداری بکاپ باید پیش از فعال‌سازی معلوم باشد؛ بازیابی بکاپ نباید گفت‌وگوی حذف‌شده را دوباره در UI قابل دسترس کند.
- برای بازیابی بکاپ، دفتر حذفِ بدون متن و محدود به شناسه/زمان حذف باید خارج از چرخهٔ restore قدیمی حفظ شود؛ پیش از بازشدن ترافیک، حذف‌ها دوباره اعمال و آزموده شوند. این دفتر هم دسترسی و مدت نگهداری مشخص دارد و جای حذف از نسخه‌های بکاپ طبق سیاست مصوب را نمی‌گیرد.
- `store:false` برای endpoint مناسب OpenAI استفاده می‌شود، اما معادل Zero Data Retention نیست. سیاست نگهداری، نوع حساب و endpoint هر برند پیش از فعال‌سازی ثبت می‌شود؛ رضایت User این تفاوت را پنهان نمی‌کند. [سیاست رسمی دادهٔ OpenAI](https://developers.openai.com/api/docs/guides/your-data).

## ۱۰. خطاها و مشاهده‌پذیری

کدهای پیشنهادی قابل ترجمه: `chat_access_denied`، `news_unavailable`، `source_scope_denied`، `model_unavailable`، `provider_unconfigured`، `quota_exceeded`، `budget_exhausted`، `provider_rate_limited`، `provider_timeout`، `generation_unknown`، `context_changed`، `citation_invalid` و `session_expired`.

کاربر پیام قابل اقدام و request_id می‌بیند؛ متن raw exception ارائه‌دهنده نمایش داده نمی‌شود. draft هنگام خطای قابل بازیابی در حافظهٔ همان صفحه حفظ می‌شود؛ در localStorage مشترک یا URL ذخیره نمی‌شود. هنگام خروج/تغییر حساب پاک می‌شود. هیچ وعدهٔ بازیابی متن ذخیره‌نشده پس از بسته‌شدن کامل مرورگر داده نمی‌شود.

شاخص‌ها: زمان صف، زمان اولین متن، زمان کل، نرخ پایان موفق/توقف/خطا، نرخ شاهد نامعتبر، تعداد سؤال بی‌پاسخ، token/cost، رزرو معلق و تلاش تکراری. تفکیک مدل/پروژه فقط برای کاربران مجاز است؛ متن چت و دادهٔ قابل شناسایی وارد labelهای metrics نمی‌شوند.

خرابی چت در dashboard خودش هشدار دارد و نباید وضعیت سالم خزش را دروغین خراب/سالم کند. circuit breaker هر ارائه‌دهنده مجزا است؛ خرابی یک برند، برندهای دیگر یا خط خبرگیری را متوقف نمی‌کند.

## ۱۱. برنامهٔ آزمون پیش از انتشار

تمام موارد این بخش **برنامهٔ آزمون** هستند و در مرحلهٔ مستندسازی اجرا نشده‌اند.

### واحد و قرارداد

۱. کاتالوگ: model_id ناشناخته، disabled، برند بدون Secret و محدودیت پروژه رد شوند.

۲. زمینه: publication→analysis→article با تطبیق پروژه، خبر حذف‌شده/منتشرنشده و منبع نامجاز آزموده شوند.

۳. بخش‌بندی: فارسی، عربی، نیم‌فاصله، emoji، ترکی و متن آمیخته؛ offset استناد دقیق باشد.

۴. پاسخ: ارجاع ناموجود، نقل‌قول ساختگی، HTML/لینک مخرب و نسبت‌دادن تحلیل AI به رسانه رد یا با هشدار روشن محدود شوند.

۵. adapterها: جریان رویداد، پایان، refusals، usage، token accounting و خطای هر سه API با fixtures مستقل آزموده شوند.

۶. هزینه: رزرو هم‌زمان، قیمت قدیمی/نامعلوم، مصرف ناقص، reasoning، cache، لغو و reconcile آزموده شوند.

### یکپارچه و امنیت

۷. دو کاربر در یک پروژه نتوانند چت هم را بخوانند؛ کاربر دو پروژه نتواند دادهٔ خبر پروژهٔ نامجاز را وارد کند.

۸. دست‌کاری شناسه، scope، مدل، زمینه، CSRF و درخواست cross-origin در همهٔ مسیرها، از جمله SSE/replay، آزموده شود.

۹. لغو عضویت/مجوز، غیرفعال‌شدن حساب و انقضای ۰۲:۰۰ حین پاسخ، اتصال بعدی را رد و خروجی جاری را در مهلت مقرر قطع کنند؛ timezone/DST با clock کنترل‌شده آزموده شوند.

۱۰. دو کلیک، دو تب و دو worker فقط یک generation محلی بسازند. restart و timeout مبهم تولید پولی خودکار تکراری نسازند.

۱۱. متن دارای دستور برای افشای چت دیگران، تغییر امتیاز، انتشار یا نشت Secret نتواند به عملیات یا دادهٔ نامجاز دست یابد.

۱۲. حذف تاریخچه هم‌زمان با stream، حذف snapshot و جلوگیری از ظاهرشدن دوبارهٔ داده پس از بازیابی بکاپ آزموده شود.

### مرورگری end-to-end

۱۳. بازکردن خبر، ارسال، سؤال پیگیری، تغییر مدل، تغییر برند با تأیید و بازکردن دوبارهٔ تاریخچه.

۱۴. کلیک ارجاع، پرش به شاهد، انتخاب یک بند، ذخیره در یادداشت و بازخورد پاسخ؛ بدون تغییر بازخورد خبر یا محتوای منتشرشده.

۱۵. هشت زبان فعلی: فارسی، انگلیسی، ترکی، عربی، اسپانیایی، ایتالیایی، آلمانی و فرانسوی؛ متن‌های پویا، خطاها، عدد/تاریخ، کاتالوگ و tooltipها.

۱۶. نمایشگر کوچک/بزرگ، منوی کناری باز/بسته، زوم ۲۰۰٪، صفحه‌کلید، screen reader، focus، کاهش حرکت و بدون CSS/JS خارجی.

۱۷. Back/Forward، لینک مستقیم، Refresh، تغییر دستیار، logout و پایان نشست؛ هیچ صفحهٔ سفید، listener دوگانه یا چت خبر قبلی روی خبر تازه باقی نماند.

۱۸. افت شبکه، quota، بودجهٔ تمام‌شده و برند قطع؛ خطا ماندگار و قابل اقدام باشد، retry تازه نیازمند اقدام کاربر باشد.

۱۹. رگرسیون ورود Google/رمزی مجاز، Reader settings، یادداشت‌ها، جست‌وجو/صفحه‌بندی، اعلان، Admin و خط خزش/انتشار. تنظیم Text direction فقط محتوای مربوط را تغییر دهد.

### کیفیت واقعی و بار

۲۰. مجموعهٔ ارزیابی پیشنهادی: ۴۰ خبر مجاز توزیع‌شده میان هشت زبان، برای هر خبر سه وظیفهٔ «استخراج واقعیت»، «پرسش نیازمند توضیح/استنباط» و «پرسش بی‌پاسخ در متن»؛ مجموع ۱۲۰ مورد پایه. حداقل ۴۰ مورد چالشی جدا شامل متن ناقص، تناقض گزارش/اصل، متن بلند، تزریق دستور و متن چندزبانه اضافه شود.

۲۱. هر مدل منتخب روی مجموعهٔ مشترک با سقف هزینهٔ معلوم ارزیابی شود. داوری خودکار/مدل کمکی تنها ابزار کمکی است؛ ادعاهای مهم و نمونه‌های خطا بازبینی دستی شوند. بدون بازبین بومی، کیفیت زبانی «تأیید انسانی مستقل» اعلام نشود.

۲۲. آزمون بار مصنوعیِ بدون provider پولی، صف/حافظه/قطع اتصال را بررسی کند. آزمایش واقعیِ محدود، زمان اولین پاسخ، صدک ۹۵ زمان کل و هزینه را اندازه بگیرد؛ نرخ خزش و تحلیل نباید به دلیل چت از بودجه یا منابع لازم محروم شوند.

### گیت‌های پیشنهادی پذیرش

- صفر نشت کاربر/پروژه و صفر عملیات مدیریتی نامجاز در مجموعهٔ امنیتی؛ شکست هرکدام مانع عرضه است.
- ۱۰۰٪ ارجاع‌های قابل کلیک به متن و نسخهٔ موجود معتبر نگاشت شوند؛ ادعای معنایی با این معیار اثبات نمی‌شود.
- هدف اولیهٔ کیفیت: دست‌کم ۹۵٪ ادعاهای خبریِ نمونه‌برداری‌شده پشتوانهٔ واقعی داشته باشند و دست‌کم ۹۵٪ پرسش‌های بی‌پاسخ درست تشخیص داده شوند؛ خطای پرریسک بررسی مستقل و مانع عرضه باشد. این درصدها هدف پیشنهادی‌اند، نه نتیجهٔ فعلی یا تضمین عمومی.
- هیچ خطای uncaught مرورگر یا شکست سناریوی اصلی در هشت زبان/اندازهٔ صفحهٔ هدف باقی نماند.
- گیت‌های هزینه، idempotency محلی، revoke و انقضای نشست پاس شوند.
- حداقل دو برند واقعی با اعتبارنامهٔ مجاز و هزینهٔ محدود end-to-end پاس شوند تا عنوان «چندبرندی فعال» صادق باشد. سرویس تنظیم‌نشده فقط به‌عنوان اتصال آماده ولی غیرفعال گزارش شود.
- هدف زمان پاسخ پس از پایلوت تعیین شود؛ timeout پیشنهادی جای SLA نیست.

## ۱۲. انتشار و برگشت

feature flag پیش‌فرض خاموش است. ابتدا کد و migration افزایشی با تست‌های ایزوله منتشر می‌شوند؛ سپس Owner در یک پروژهٔ آزمایشی، مدل‌ها، مجوز کاربران و سقف هزینه را فعال می‌کند. هیچ کاربر یا پروژهٔ واقعی خودکار وارد آزمایش نمی‌شود.

نسخهٔ image و commit، مدل/نسخهٔ prompt، سیاست زمینه و قیمت ثبت می‌شوند. آزمون ساختگی به‌عنوان موفقیت API واقعی گزارش نمی‌شود. rollout پس از سنجش کیفیت و مصرف گسترش می‌یابد.

در خطای جدی، flag خاموش و generationها drain/لغو می‌شوند؛ بخش خبرخوان بدون چت باید سالم بماند. rollback تصویر، schema و تاریخچهٔ افزوده را حذف نمی‌کند. فقط سرویس Researcher در محدودهٔ انتشار است؛ compose کامل، Contenter، Consultant و اعتبارنامه‌های مشترک دست‌نخورده‌اند.

## ۱۳. مراحل بعد که به تأیید نیاز دارند

تأیید دامنهٔ نسخهٔ اول در سند محصول، پیش‌نیاز شروع توسعه است. انتخاب سقف مالی واقعی و مجوز ارسال متن به هر برند، قبل از فعال‌سازی لازم‌اند. نام دقیق مدل‌ها پس از بررسی رسمی روز اجرا و حساب مجاز نهایی می‌شود؛ در این مرحله تصمیم یا مصرف واقعی به جای Owner انجام نشده است.

برای مرحلهٔ جست‌وجوی وب، منابع و هزینهٔ ابزار مستقل لازم است. مستندات Gemini نشان می‌دهد ابزار Search می‌تواند هزینهٔ جداگانه و استناد وب داشته باشد؛ بنابراین انتخاب برند به‌تنهایی نباید جست‌وجوی وب را بی‌خبر فعال کند. [راهنمای رسمی Google Search Grounding](https://ai.google.dev/gemini-api/docs/google-search/).
