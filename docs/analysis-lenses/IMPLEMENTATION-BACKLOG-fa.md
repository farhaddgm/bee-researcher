## ۲. شرح و تعریف پایان هر گام

### گام ۱ — تثبیت و تطبیق

آخرین main، schema head، قرارداد فعلی چت/Voice/Research و تغییرات هم‌زمان بررسی شوند. branch با پیشوند `codex/` در checkout اختصاصی و تمیز بسازیم؛ تغییرات root workspace و پروژه‌های دیگر دست‌نخورده بمانند.

Done: diff دامنه، قرارداد optional analysis_profile، تعداد پنج خبر در مجموع، عدم web/Report و سیاست defaults ثبت شده‌اند. هر انحراف از بسته، ADR تازه با دلیل دارد؛ حذف الزام امنیت برای آسان‌کردن اجرا مجاز نیست.

### گام ۲ — schema، compiler و قالب‌ها

schema تایپ‌شده و محدود برای تعریف/ابعاد/ترجمه/خروجی، hash canonical و compiler زیر قواعد پایه ساخته شود. چهار لنز از [کاتالوگ](LENS-CATALOG-fa.md) به دادهٔ versioned seed تبدیل شوند. مثال‌های آزمون از promptهای عادی جدا باشند.

Done: طول مجموع، inactive، duplicate، output sections و دستور مشکوک تست شده‌اند؛ template قابل بازتولید است و priority به score انتشار تبدیل نمی‌شود.

### گام ۳ — داده و migration

مدل‌های لنز/revision/policy/preview/discovery و نتیجهٔ nullable generation در schema Researcher اضافه شوند. FK مرکب، uniqueness، optimistic locking، indexes و TTL را با PostgreSQL واقعی بررسی کنیم. migration به head واقعی متصل و شماره در همان زمان تعیین شود.

Done: forward-schema با تصویر قبلی، پاک‌سازی و retention آزموده؛ هیچ تغییر credential/session/DB سرویس‌های دیگر وجود ندارد. seed ویرایش مالک را reset نمی‌کند.

### گام ۴ — چرخهٔ مدیریت

CRUD ساختاریافته، validate رایگان، restore، archive، revoke و publish atomic با authorization واقعی Owner و CSRF پیاده شوند. active/default pointers معتبر بمانند. audit فاقد محتوای خصوصی باشد.

Done: دو تب/دو worker conflict درست دارند؛ draft آزموده‌نشده یا تغییرکرده publish نمی‌شود. default بدون جایگزین حذف نمی‌شود. صرف مخفی‌شدن دکمه معادل امنیت نیست.

### گام ۵ — زمینه و worker

تعریف immutable لنز و analysis_version به context خصوصی افزوده شوند؛ context.version منبع فعلی حفظ شود. admission، queue، stream، follow-up، close/save و revocation به همان engine وصل باشند. clients قدیمی و intentهای مستقل بی‌لنز دست‌نخورده کار کنند.

Done: اجرای N هنگام publish N+1 ثابت، لغو دسترسی مؤثر و close-before-create/running بدون resurrection است. private context بدون انتخاب وارد prompt نمی‌شود.

### گام ۶ — نتیجه و مصرف

schema خروجی برای lens_analysis با adapterهای مدل‌های فعال، validation server، renderer امن و answer متنی برای history ساخته شود. کنترل اندازهٔ ورودی/خروجی، بودجه/توکن، idempotency، unknown usage و cancellation reuse شوند.

Done: invalid JSON/source/dimension خروجی معتبر نمی‌شود؛ retry پولی پنهانی نیست؛ price و model انتخابی با provenance ثبت می‌شوند. providerهای فاقد قابلیت پذیرفته‌شده با دلیل مناسب رد شوند.

### گام ۷ — کشف هاله

جست‌وجوی bounded از دادهٔ منتشرشدهٔ همان پروژه، normalization/aliasهای چندزبانه، گروه‌بندی تکرار، دلیل با شاهد، snapshot و pagination ساخته شود. `as_of`، expiry، coverage و وضعیت نبود داده آشکار باشند.

Done: پنج خبر شامل مرکز enforce می‌شود؛ ACL در کشف و اجرا معتبر؛ corpus بیش‌ازحد به ادعای پوشش کامل تبدیل نمی‌شود. کیفیت ناکافی در eval سبب بازنگری retrieval است، نه ساختن پیشنهاد با حدس.

### گام ۸ — preview مالک

audience صریح owner_preview با نشست Admin، مجوز منابع و بودجهٔ فعلی ساخته شود. snapshot مقایسهٔ نسخه‌ها، مدل یکسان، rubric تأیید و TTL ۲۴ ساعت لازم‌اند. preview به User memory منتقل نشود.

Done: ادمین به cookie User نیاز ندارد؛ دادهٔ Owner دیگر خواندنی نیست؛ هر paid run واضح و قابل توقف است. ویرایش نسخه/منابع/مدل تأیید قبلی را باطل می‌کند.

### گام ۹ — رابط مالک

component فقط Settings، یک نشان Owner only، فرم ساده و ردیف ابعاد با reorder کیبورد و preview پایدار ساخته شود. توضیحات در i و errors کنار فیلد باقی بمانند. draft-save، preview و publish قابل تفکیک باشند.

Done: component به صفحات دیگر نشت نمی‌کند؛ sidebar toggle مسیر را عوض نمی‌کند؛ ارتفاع/رنگ/عرض دکمه‌ها با الگوی موجود هم‌خوان است و CSS از اولین رندر اعمال می‌شود.

### گام ۱۰ — رابط کاربر

دو select مستقل دامنه/لنز، i، discovery selection، جواب معتبر و composer فعلی در پنجرهٔ خبر و میز پژوهش reuse شوند. فرصت/ریسک فعلی حفظ و به چارچوب انتخاب‌شده وصل شوند. تغییر چارچوب شاخهٔ تازه و رضایت روشن داشته باشد.

Done: بازکردن یا تغییر select هزینه ندارد؛ insufficient حالت درست دارد؛ متن اصلی خبر بازنویسی نمی‌شود؛ Save/close و private memory مطابق قرارداد فعلی‌اند.

### گام ۱۱ — پذیرش جامع

تمام سناریوهای [آزمون](ACCEPTANCE-PLAN-fa.md)، هشت زبان، چهار عرض، sidebar، voice، log privacy، SQL race و regressions اجرا شوند. کیفیت واقعی با modelهای واجد شرایط، مجموعهٔ مستقل و budget cap معلوم بررسی شود. مسلط‌بودن ظاهری مدل جای شاهد نیست.

Done: رسیدها موجود؛ موارد مصنوعی و واقعی تفکیک شده‌اند؛ هیچ gate با skip غیرموجه سبز نیست. عدم وجود بازبین انسانی یا کمبود شواهد صریح گزارش شود؛ «پذیرش انسانی» جعل نشود.

### گام ۱۲ — انتشار و پایان

نسخهٔ برنامه فقط پس از توسعه انتخاب شود؛ این بسته release number تازه تعیین نمی‌کند. release note واقعی، PR/CI، تصویر امضاشده و binding commit، backup/migration محدود، deploy فقط Researcher و smoke انجام شود. قابلیت ابتدا با flag خاموش، سپس canary محدود با دادهٔ مجاز و بعد فعال‌سازی انجام شود.

Done: نسخه/commit/digest/schema واقعی در رسید تحویل، مدل‌های واجد شرایط و محدودیت‌های واقعی مستند، rollback تمرین‌شده و هیچ اثر بر Contenter/Consultant یا دادهٔ پروژهٔ واقعی بدون مجوز وجود ندارد.

## ۳. وابستگی‌ها و اقدام موردنیاز

برای همین مستندسازی اقدامی از کاربر لازم نیست. برای توسعه، نیاز به ساخت account/service/کلید جدید صرفاً برای «لنز» نداریم؛ AI و زیرساخت فعلی reuse می‌شوند. این ادعا به معنی سالم‌بودن یا داشتن موجودی فعلی همهٔ providerها نیست؛ در آغاز گام ۱ بررسی خواهند شد.

پذیرش واقعی AI به credential سالم، مدل مجاز، اجازهٔ پرداخت آزمون و محیط قابل دسترس نیاز دارد. اگر آن مرحله نیاز به اقدام مالک پیدا کند، توضیح امن و مرحله‌به‌مرحله داده شود؛ secret در چت خواسته نشود. در مستندسازی فعلی هیچ API پولی فراخوانی نشده است.

کسب‌وکار، حافظه و خبرهای واقعی نباید به صورت خودکار برای آزمایش انتخاب شوند. fixtureهای مجاز و مستقل بهترین پیش‌فرض‌اند. شرایط preview ترجمه‌شده و تأیید ادعاهای حساس باید قابل مشاهده باشد.

## ۴. پس از نسخهٔ اول؛ شروع‌نشده و غیرمتعهد

۱. بازیابی semantic چندزبانه پس از benchmark مدل/ایندکس و حریم خصوصی.

۲. web research مستقل با منابع واقعی، اجازهٔ روشن، هزینه/زمان محدود و حفاظت SSRF/محتوای غیرقابل اعتماد.

۳. لنز اختصاصی پروژه با وراثت صریح و تفاوت نسخه‌ها.

۴. مقایسهٔ دو یا سه لنز با هزینهٔ آشکار و منابع یکسان.

۵. لنزهای استراتژی، مالی، مقررات و عملیات با معیارهای تخصصی مناسب.

۶. تحلیل گزارش‌های محرمانه در پرتال مجاز خودشان، بدون مخلوط‌کردن با User/publication.

این‌ها ایدهٔ آینده‌اند، جزو Done نسخهٔ اول نیستند و به‌عنوان کار انجام‌شده گزارش نخواهند شد.
